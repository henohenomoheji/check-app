# システム構成設計書

## 1. 検討状況・前提

- Next.jsの画面とAPIは、同じAzure App Serviceに配置する案とする。
- 文書解析・関連ナレッジ判定のバックグラウンド処理について、Functionsなし／ありを比較する。採用案は未確定。
- ファイル上限は、1ファイル20MB、最大5件（合計100MB）を想定する。正式な上限、対応形式、ページ数は要件確定時に決める。
- どちらの案でも、Blob Storage、PostgreSQL、Document Intelligence、Azure OpenAIを利用する。
- 参照ナレッジは、管理者側がBlob Storageにテキスト（`.txt`）またはMarkdown（`.md`）ファイルとして配置する。
- アップロード経路は別途決定する。ブラウザーからBlobへの直接アップロードは、どちらの案でも選択できる。
- 既存図：`../Azureアーキテクチャ.drawio.png`。以下の配置・処理経路は今後図へ反映する。

## 2. Next.jsとAPI・バックグラウンド処理の配置

| 責務 | 案A：Functionsなし | 案B：Functionsあり |
|---|---|---|
| 画面表示 | App Service上のNext.js | App Service上のNext.js |
| 認証・認可、アップロード受付 | Next.js API | Next.js API |
| 判定開始、状態・結果取得、会話履歴取得 | Next.js API | Next.js API |
| 実行待ちジョブの保持 | PostgreSQLなどの永続ジョブ管理 | キュー（Azure Queue Storageなど） |
| 文書解析・AI判定の制御 | App Service上のバックグラウンドワーカー | Azure Functions |
| 原本・解析結果保存 | Blob Storage | Blob Storage |
| 会話・実行状態・判定結果保存 | PostgreSQL | PostgreSQL |

### 2.1 案A：Functionsなし

1. 原本をBlobに保存し、APIがDBに実行情報とジョブを登録する。
2. APIは実行IDを返し、画面は状態取得APIで進捗を確認する。
3. App Service上のワーカーがジョブを取得し、文書解析・AI判定を進める。
4. ワーカーがBlob・DBに結果を保存する。

採用前に、App ServiceのOS・プランに合わせたワーカーの起動・常駐方法を具体化する。Next.jsのAPIから非同期処理を開始するだけの実装にはしない。再起動後のジョブ再開、取得ロック、再試行、重複実行防止を設計する。

### 2.2 案B：Functionsあり

1. 原本をBlobに保存し、APIがDBに実行情報を登録する。
2. APIがキューへ実行IDなどの参照情報を登録し、画面に実行IDを返す。
3. Functionsが実行依頼を取得し、文書解析・AI判定を進める。
4. FunctionsがBlob・DBに結果を保存し、画面は状態取得APIで進捗を確認する。

キューにファイル本体は格納しない。DB登録とキュー登録の間で失敗した場合の回復、再配信時の重複実行防止、失敗ジョブの再実行方法を設計する。解析待ちの管理方式と、Functionsの実行プラン・タイムアウト・並列数を決める。

## 3. Functionsなし／ありの選定条件

利用人数だけで決めず、ピーク時の処理量、許容待ち時間、運用方法を合わせて判断する。20MB × 5件というサイズだけでは、Functions採用の必須条件にはならない。

| 判断項目 | 案A：Functionsなしを選ぶ条件 | 案B：Functionsありを選ぶ条件 |
|---|---|---|
| ピーク負荷 | 想定負荷試験で、画面・APIと解析処理を同居させても性能目標を満たす | 処理の集中に備えて、画面・APIと解析処理を別々に拡張したい |
| 許容待ち時間 | 並列数を制限しても、実行待ちを含む完了時間が目標内に収まる | 処理側の実行能力を独立して調整する必要がある |
| ワーカー運用 | 常駐・再起動・ジョブ再開の方法を具体化でき、運用できる | キューを契機とする実行基盤を利用したい |
| 障害・リリースの影響 | 画面・APIと処理が同じ実行環境であることを許容できる | 画面・APIと処理の障害やデプロイの影響を分離したい |
| コスト・管理 | ワーカー分を含むApp Service容量と運用負担が妥当 | Functions・キューを追加した総コストと管理負担が妥当 |

案Bでも、Document Intelligence・Azure OpenAIの利用上限を超えて処理できるわけではない。両案で並列数・再試行間隔を制御する。処理時間が長いことだけを理由に案Bへ決めず、待機・再開の設計も比較する。

### 3.1 選定に必要な確認値

| 項目 | 現状 | 確認方法 |
|---|---|---|
| 利用対象人数 | 未確定 | 利用部署・対象者を確認 |
| ピーク時の判定開始数（件／分） | 未確定 | 同時利用シナリオを確認 |
| 1判定の平均・最大ファイル数、ページ数 | 最大5ファイルを想定、ページ数未確定 | 代表資料と入力上限を確認 |
| 抽出文字量・AI入力トークン量 | 未確定 | 代表資料を解析して測定 |
| 平均・遅いケースの処理時間 | 未測定 | 代表資料で解析から判定完了まで測定 |
| 許容完了時間・画面/API応答時間 | 未確定 | 業務上の性能目標を設定 |
| 障害時の復旧目標 | 未確定 | 再起動・処理失敗時に許容できる復旧時間を確認 |

処理中の判定数の概算は「1分あたりの判定開始数 × 平均処理時間（分）」で見積もる。これは容量を保証する値ではなく、負荷試験条件を作るための目安とする。文書解析待ちが多い場合、処理中件数とApp ServiceのCPU負荷は比例しないため、CPU・メモリ・DB接続数も実測する。

### 3.2 決定手順

1. 入力上限、ピーク利用条件、性能・復旧目標を決める。
2. 代表資料と最大入力条件（20MB × 5件）で処理時間・資源使用量を測る。
3. 想定ピーク時に、画面・API応答とジョブ完了時間を確認する。
4. 再起動時の再開、失敗時の再試行、重複実行防止を確認する。
5. 案Aが目標を満たし、ワーカー運用を具体化できるなら案Aを採用候補とする。独立した拡張・運用が必要なら案Bを採用候補とし、実行プランと外部サービス上限を含めて検証する。
6. 総コストと運用負担を比較し、採用案と理由を記録する。案Aの試験失敗が、案Bの性能を保証するものではない。

## 5. ナレッジの登録・更新経路

### 5.1 決定事項

- 管理者側がナレッジをテキスト（`.txt`）またはMarkdown（`.md`）ファイルとしてBlob Storageに配置する。
- アプリケーション内のナレッジ管理画面は初期リリースの対象外とする。
- 配置済みのテキスト・Markdownを判定・追加質問の参照内容として読み込む。このナレッジの読み込みにDocument Intelligenceによる文書解析は使用しない。利用者がアップロードする資料の解析とは別の経路とする。
- ナレッジの配置・更新経路は、Functionsなし／ありの両案で共通とする。

### 5.2 登録・更新の基本経路

1. 管理者側がテキスト・Markdownファイルを準備する。
2. 管理者側がBlob Storageのナレッジ用領域に配置・更新する。
3. アプリケーション側が公開対象のナレッジを特定し、判定・追加質問時に内容を取得する。公開対象の管理方法と更新反映タイミングは未確定。

### 5.3 今後決める内容

| 項目 | 検討内容 |
|---|---|
| 配置方法・権限 | 管理者が使用するアップロード手段、書き込み権限、アプリの読み取り権限 |
| 格納構成 | ナレッジ用コンテナー／プレフィックス、ファイル命名規則、文字コード |
| DBとの対応 | 既存の`knowledge`テーブルにID・タイトル・Blob格納先・版を登録する方法。本文が配置済みファイルの場合、`extracted_text_path`の役割を見直す |
| 更新の検出・反映 | 判定時に一覧を取得するか、管理者の登録処理や定期同期などでDBへ反映するか。キャッシュの更新方法 |
| 版管理 | 上書き／版別ファイルのどちらにするか。判定に使用した版を固定し、過去の根拠を再現できるようにするか |
| 複数ファイルの公開 | 更新中の新旧ファイルが混在しないよう、公開対象の一覧や切り替え方法を定めるか |
| 削除 | 判定対象から除外するタイミングと、過去の判定で参照した資料の保持方法 |
| 根拠・原本リンク | テキスト・Markdownの見出しや行などを根拠位置として扱うか。元資料のページ番号・原本リンクが必要な場合、その対応情報をどこに保持するか |
| AIへの入力方式 | ファイル件数・総テキスト量を確認し、全件入力／候補検索の方式を決める |

テキスト・Markdownの配置だけでは、元資料のページ番号や元資料へのリンクは確定しない。要件の「ページ番号・原本リンク」との対応は、要件・DB設計で合わせて確認する。

## 6. Blobの格納構成、アップロード・原本配信方式

本節は推奨案・比較案として記載する。ネットワーク条件が未確定のため、直接アクセス／App Service経由の採用は未決定。Functionsなし／ありの選択とは独立して判断する。

### 6.1 格納構成（推奨案）

開発・検証・本番でストレージアカウントを分け、各環境で用途別に3コンテナーを設ける。

| コンテナー | 保存内容 | Blob名の例 |
|---|---|---|
| `uploads` | 利用者の入力原本 | `{file_id}/original.pdf` |
| `extractions` | 抽出文章・解析JSON | `{file_id}/{extraction_id}/content.txt`、`result.json` |
| `knowledge` | 管理者が配置するテキスト・Markdown | `{knowledge_id}/{version}/content.md` |

- 元ファイル名はDBに保持し、Blob名にはシステムが発行するIDを使用する。
- 再解析では新しい`extraction_id`の配下に保存する。ナレッジは版別のパスで保持することを推奨する。
- DBにはコンテナー名・Blob名・必要に応じて版識別子を保存する。SASなどの期限付きURLは保存しない。
- パスやコンテナーの分割だけで利用者間の認可を保証しない。APIでDB上の所有者・会話との対応・公開範囲を確認する。
- 匿名アクセスはストレージアカウントで無効にする。これはPublic Endpointの利用可否とは別の設定である。

### 6.2 案C：ブラウザーからBlobへ直接アクセス

ブラウザーからBlobへネットワーク接続できる場合の案。合計100MBのファイル本体をApp Serviceで中継する負荷を減らせるため、接続条件を満たす場合の第一候補とする。

#### アップロード

1. ブラウザーがAPIにファイル名・申告サイズ・アップロード先の会話を送信する。
2. APIが認証・認可、最大20MB／最大5件、形式などを確認し、ファイルIDとアップロード用のDB情報を登録する。
3. APIが対象の1つのBlobに必要な書き込み権限だけを付与した、短時間有効なユーザー委任SASを発行する。発行にはApp ServiceのManaged Identityと必要なRBAC権限を使用する。
4. ブラウザーがBlobへ各ファイルをアップロードし、APIに完了を通知する。
5. APIがBlobの存在・実サイズ・所有権・形式などを検証し、解析対象として確定する。ブラウザーからの完了通知だけでは確定しない。

SASでは20MBの上限を直接強制できないため、事前確認に加え完了後の検証を行う。未完了・上限超過ファイルの削除方針を決める。書き込みSASが有効な間の変更に備え、解析対象を不変のBlobへコピーする、Blobの版を固定するなどの確定方法を決める。

ブラウザー向けCORSはアプリのOriginと必要なメソッド・ヘッダーに限定する。CORSは認証・認可の代わりにはならない。

#### 原本配信

1. ブラウザーがAPIにファイルIDまたはナレッジIDを指定して参照を要求する。
2. APIが会話・ファイル・ナレッジの参照権限を確認する。
3. APIが対象Blobだけの短時間有効な読み取り専用SAS URLを返す。
4. ブラウザーがBlobから原本を取得する。

SAS URLは期限内なら所持者が利用できるため、会話本文・DB・アプリのログに保存しない。期限切れ時はAPIで再度認可して再発行する。

### 6.3 案D：App Service経由でアップロード・配信

ブラウザーからBlobへ到達できず、App ServiceからBlobへ到達できる場合の案。例えば、BlobをPrivate Endpoint経由に限定し、利用端末にはそのネットワークへの接続経路がない場合に候補となる。

#### アップロード

1. ブラウザーがNext.js APIへファイルを送信する。1ファイル単位で送信し、アップロードの並列数を制御する。
2. APIが認証・認可、件数・形式を確認し、受信中のバイト数でも20MBの上限を検証する。
3. APIがManaged IdentityでBlobへ保存する。100MB全体をメモリに保持する実装を避け、ストリーミング転送などを検討する。
4. 保存・検証後にDBの状態を確定する。途中失敗時の再送・一時Blobの削除方法を定める。

Next.jsの実装方式、App Serviceや前段プロキシのリクエストサイズ・タイムアウト、同時転送時のメモリ・通信負荷を確認する。

#### 原本配信

1. ブラウザーがNext.js APIへ原本の参照を要求する。
2. APIが参照権限を確認し、Managed IdentityでBlobから取得する。
3. APIがファイルをブラウザーへストリーミング配信する。

PDF閲覧などに必要なRangeリクエストへの対応、Content-Type・Content-Disposition、機密資料のキャッシュ方針を設計する。ブラウザーにBlob向けSASを渡す必要はないが、原本転送はApp Serviceの負荷となる。

Private Endpointを採用する場合は、App Service側のVNet統合・DNS・Blobへの到達性を確認する。Functionsを利用する場合はFunctions側の接続、Document IntelligenceにBlobを直接参照させる場合はそのサービス側の接続・権限も別途確認する。

### 6.4 ネットワーク条件と選定条件

| 項目 | 案C：Blobへ直接アクセス | 案D：App Service経由 |
|---|---|---|
| ブラウザーの接続先 | App ServiceとBlob | App Service |
| ネットワークの前提 | 利用端末からBlobへ到達できる | App ServiceからBlobへ到達できる |
| 認証・認可 | APIの認可後、対象Blob限定SASでアクセス | APIが毎回認可し、サーバー側でBlobにアクセス |
| 転送負荷 | ファイル本体がApp Serviceを通らない | ファイル本体がApp Serviceを通る |
| 主な実装事項 | SAS発行、CORS、アップロード後検証、版の確定 | ストリーミング、サイズ制限、Range対応、転送タイムアウト |
| 選ぶ条件 | 端末からのBlob接続と期限付きURLの利用が社内方針上許可される | Blobへの端末アクセスを禁止・制限する、またはAPI経由で配信を管理したい |

Public Endpointでも匿名公開は不要。Private Endpointでも社内端末がVPNなどと適切なDNSを通じて到達できれば案Cを選べる。SASはネットワーク制限を回避しないため、Public／Privateの名称だけで決めず、実際の利用端末からの到達性を確認する。

選定前に、社内のBlob公開ネットワーク方針、端末の接続元・VPN・DNS、SAS利用可否、最大入力時の転送時間・App Service負荷を確認する。採用案とSAS有効期限・並列数などの設定値は未確定とする。

### 6.5 閲覧・ダウンロードの扱い

| ファイル | 表示・配信案 |
|---|---|
| PDF・画像 | ブラウザー閲覧とダウンロード |
| テキスト・Markdown | アプリ内表示と元ファイルのダウンロード。Markdownの埋め込みHTMLなどは安全に扱う |
| 解析JSON | 通常の利用者向け原本配信には含めない |

ナレッジの元資料が別に存在する場合、その原本の保存先・リンクは別途設計する。保存期間、会話削除に伴う削除、未完了アップロードの清掃、過去の判定が参照する版の保持期間も後続設計で確定する。
